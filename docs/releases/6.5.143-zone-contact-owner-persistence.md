# Cloud 6.5.143 — zone-contact ownership persistence

DEMO / PAPER ONLY.

## Defect isolated

A qualified `HTF_ZONE_CONTACT_HANDOFF` could acquire ownership against an existing
base lifecycle row that was still `ARMED`. The ownership fields were persisted,
but the row status remained `ARMED`.

Live ownership truth intentionally recognizes only non-terminal execution-owner
states (`INTERACTING`, `REACTION_CONFIRMED`, `OBJECTIVE_IN_PROGRESS`). On the
next live sync the newly acquired contact owner therefore disappeared even though
its acquisition timestamp and anchor still existed. This produced the contradictory
state seen in validation: macro/M1 handoff remained active while the dashboard and
Sequence reported no acquired thesis lock.

Sequence 3.75 then correctly failed closed when canonical proof requested the current
owner identity, which could make a valid post-sweep M1 sequence appear "shy".

## Surgical correction

When `HTF_ZONE_CONTACT_HANDOFF` acquires an existing `ARMED` source lifecycle,
Cloud now promotes only that lifecycle status to `INTERACTING`.

It does **not** mark the reaction confirmed and does **not** change:

- attached BSL/SSL selection or the Sequence 3.75 canonical-liquidity gate;
- Model 1, Model 2 or Model 3 confirmation rules;
- the universal CLOSED-M1 directional-entry gate from Sequence 3.74;
- P0/R1/R2 limits or freshness;
- stop-loss geometry, RR, risk sizing or targets;
- M15 invalidation, accepted-zone flip logic or trade management.

A new regression test proves that an envelope-contact owner acquired from an
`ARMED` base row remains a live `INTERACTING` owner while
`reaction_confirmed_at` stays zero.

- Cloud: 6.5.143
- Stable MT5 package: 6.4.16 (unchanged)

No MT5 installer or EA reattachment is required for this Cloud-only correction.
