# Cloud 6.5.139 / MT5 Stable 6.4.12 — Sequence 3.72 terminal-flat ownership and execution-context truth

## Scope

- Cloud: 6.5.139
- MT5 stable package: 6.4.12
- Sequence EA: 3.72
- DataBridge: 1.58 unchanged
- DEMO / PAPER ONLY

## Live defects addressed

### 1. Terminal flat campaign could retain execution monopoly

A valid acquired thesis could complete P0, R1 and R2, close every Sequence position through normal management, and still keep the ownership lock because its final liquidity objective had not printed.

That state was internally consistent with the old ownership contract but operationally wrong:

- Sequence had no legal R3 slot;
- no position remained open;
- the thesis objective could remain valid as historical/lifecycle truth;
- yet every newly ranked opposite zone remained WATCH ONLY.

Cloud 6.5.139 separates **thesis lifecycle truth** from **execution monopoly**.

A terminal-flat execution lock is released only when a fresh Sequence heartbeat proves all of the following:

1. the heartbeat campaign key exactly matches the frozen owner campaign;
2. Sequence reports zero open positions;
3. P0 has occurred;
4. Sequence reports either `REENTRY_CAP_REACHED` or `THESIS / REENTRY_LIMIT_REACHED`.

The release persists separately as:

- `ownership_execution_released_at`
- `ownership_execution_release_reason=TERMINAL_FLAT_CAMPAIGN_ENTRY_CAP_EXHAUSTED`

It does **not** set `objective_complete_at`, does **not** set `invalidated_at`, does **not** erase the ownership acquisition history, and does **not** permit the same exhausted lifecycle to reacquire as a new P0.

A temporary flat period before R1/R2 therefore cannot release the owner.

### 2. Accepted-zone flip gate was displayed under the wrong map zone

Sequence correctly preserved failed-zone geometry for accepted-flip execution, but after each evaluation it restored the current Cloud plan. Heartbeat identity therefore described the current map while the gate could still belong to the persisted failed-zone flip.

Sequence 3.72 publishes an explicit active execution context:

- `THESIS_OWNER`
- `MAP_PLAN`
- `ACCEPTED_ZONE_FLIP`

For an accepted flip it publishes:

- source analysis id;
- source failed-zone id;
- opposite execution direction;
- F0 / FR1 / FR2 slot;
- accepted-invalidation timestamp;
- source core and envelope;
- preserved flip target ladder;
- source contract fingerprint and source-specific contract verification.

Cloud/dashboard now show that execution object separately from the newly ranked HTF map.

### 3. Current-map parity could mask the true blocker

The dashboard previously allowed a current-map sniper-contract mismatch to visually override an already-terminal `REENTRY_LIMIT_REACHED` gate. It could also apply current-map parity semantics while a persisted accepted flip was the actual execution object.

Cloud 6.5.139 now:

- gives terminal campaign exhaustion precedence as the immediate blocker;
- uses the accepted-flip source contract truth while that context is active;
- exposes exact Cloud-vs-Sequence values for parity mismatch fields.

## Management invariants

This release does **not** change the validated trade-management logic.

The complete `ManagePositions()` body in Sequence 3.72 is required by regression test to be identical to 3.71, including:

- break-even logic;
- near-target 85% / 95% high-water arming;
- 60% / 80% target-distance locks;
- objective ratchets;
- M5 runner trailing;
- broker stop-distance handling.

It also does not change:

- P0/R1/R2 maximum campaign count;
- entry confirmation models;
- protected M1 swing stops;
- minimum RR;
- risk matrix;
- accepted-invalidation definition;
- objective geometry;
- position sizing.

## Safety principle

A thesis can remain valid historical/lifecycle context without indefinitely blocking unrelated new execution after its complete P0/R1/R2 risk campaign is flat and exhausted.

Conversely, zero positions alone never releases ownership. Exact campaign identity and an explicit terminal Sequence gate are mandatory.
